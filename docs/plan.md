# Plan

## Goal

A game where many players play noughts and crosses together on one big field, each with their own shape: "Boter, Kaas en Eieren Ultra". It is played online and live, each player on their own device, in a room, or together on one screen. Version 1 was plain tic-tac-toe (3×3, two players); the field, the number in a row and the number of players (two to twelve) are chosen by whoever makes the game, and every player chooses one of the twelve shapes.

## Decisions

- **Online, live.** Players join a room and see each other's moves immediately.
- **Version 1 is classic 3×3 with two players**, but the engine is already written for N players, any field size and any winning length.
- **Games can be watched again.** A game is its config plus its moves, which the engine keeps; `replayGame` reads a stored game back and `stateAfter` steps through it. Saving the games and the replay screen are milestone 4.
- **Finished games are kept in an archive.** A second Durable Object class, `Archive` (SQLite storage, one object named `games`), holds every finished game of every room, so it outlives the room, which is deleted a day after its last move. It was chosen over D1 because it needs no database to create and no extra rights for the deploy token, and a pull request's preview Worker gets an archive of its own, like its rooms; one object holds about 10 GB, and a game is a few hundred bytes, so a family never gets near it. A game is saved by the room at the moment the move that wins or draws it is played, whoever is still connected, and once: the room gives it a random id (96 bits, 16 URL-safe characters, `/api/games/:id`) and puts the game in a queue in its own storage (`server/archive-queue.ts`), which survives a failed call, a sleeping room and a rematch: the room's alarm tries again every 30 seconds with the same id (20 times at most, then it is logged and dropped) and the room isn't deleted while a game waits. The players are told the id (`gameId` in the `state` message) only once the archive has confirmed the game, so a link never leads to a game that isn't there yet; the time kept is the moment the game ended. A stored game also says when it started (`startedAt`, the first move of the round, set by the room; with `finishedAt` it gives the duration; games kept before this have none and are left out of anything about duration, not guessed). A game that nobody finishes is **dropped**: it has no result, and the room that held it expires. Stored games are never deleted.
- **Who may see a game.** Anyone who has the id, and nobody who doesn't: the id is the link, and it can't be guessed. The repository is public but the games aren't. A game holds the shapes' moves and the names that were typed, never a token. The tokens of the players are kept only as SHA-256 hashes, in a table of their own, to find "your games" again (#17): a list is only for the browser that played, and there is no list of everybody's games. The list is `/spellen` (this browser's games, newest first, 20 at a time, the next page after the last game of the one before); a game is `/spel/<id>`, and a link to one that doesn't exist, or can't be read, says so. "Play again" from a game makes a new room for as long as every game is the classic 3×3 with two players; once the field and the shapes can be chosen, it should start a room with the same config.
- **Statistics (#48).** Decided with Vincent on 2026-10-18. **Whose:** both. The page Statistieken (`/statistieken`) shows the numbers of all finished games together, to anyone who opens it (it holds only counts and shapes: no names, no tokens, no moves of a single game), and the page of played games gets a few lines about the games of this browser, found through the hashed token like the list. **How they are kept:** worked out from the archive when asked, never as counters: `GET /api/stats` reads every stored game, `computeStats` (`shared/stats.ts`, pure, tested on a made-up set) counts, and a browser may keep the answer for 30 seconds. A family never plays enough games to make that slow, and the numbers are always right, since they can be rebuilt at any moment. **What counts:** finished games only; a game that nobody finishes is dropped, as it is now. Days, weeks and hours are counted in Dutch time (`Europe/Amsterdam`). Anything about how long a game took leaves out games without `startedAt`; the players X and O of old games are read as the cross and the circle. The time of every move is **not** kept (so no thinking time per player, nor a fastest or slowest move); the rooms that were made and the rounds each had **are**: a room has an id of its own (`room-id` in its storage, since the code is used again once a room is gone), notes itself in the archive when it is made (`rooms` table: id, time, seats; a failed note only loses one count, the room still works), and every game it hands over carries that id in a `room_id` column next to the game and never in it, so a room's rounds are its games. Rooms and games from before this have no id and are not counted as rooms.
- **TypeScript, React and Vite on Cloudflare.** The same set-up as [Blokhut](https://github.com/VincentSmedinga/blokhut): pnpm, Node 24, Vitest, Playwright, Storybook, Cloudflare, Conventional Commits, pull requests only. Realtime through Durable Objects.
- **One Cloudflare Worker for the site and the rooms.** A Durable Object can't live in a Pages project, so the app is a Worker with static assets (`wrangler.jsonc`, `@cloudflare/vite-plugin`) and the rooms are Durable Objects in the same Worker; `pnpm dev` runs all of it in one Vite server. A pull request's preview is a Worker of its own (`tic-tac-toe-ultra-pr-<number>`, with its own rooms), deleted when the pull request closes, because Workers with Durable Objects get no version-URL previews. SQLite-backed Durable Objects run on the Workers Free plan; the WebSocket Hibernation API keeps an idle room free of duration charges.
- **Players can type an optional name.** It is kept in the room, not in an account; the shape is what identifies a player.
- **A room has two to twelve seats.** Whoever makes the room says how many (two when nobody says), together with the field (`players` in the body of `POST /api/rooms`, validated with the field). The first to join is the one who made it and holds the first seat; the seats are named `X`, `O`, `3`, `4`, … in order. The game starts by itself when every seat is taken and every person has chosen a shape, and the one who made the room can also start it earlier, with the people who are there, when there are at least two and all have chosen (`start` message, "Start met 3 spelers"). From then on nobody new can sit down (`game-started`); the people who play stay for the rematches, with the seats that were left over staying empty. The turn order is the order of the seats, and every round the starting player moves one seat on. **When somebody doesn't come back the game waits for them**, as it does with two; a way to go on without them is for later. **The name is "Boter, Kaas en Eieren Ultra"** from here on, with capitals, as one title: "Ultra" is part of the name and not a label next to it, since it is what the game is once it can be played with many people on a bigger field. It is the title of the page, of the screen and of the README.
- **The field of a room is chosen by whoever makes it.** The room keeps it (`field` in its state, so a room that sleeps remembers it, and a room from before this is classic 3×3), `POST /api/rooms` takes it (`{ width, height, winLength }`, validated with zod; no body is classic), every `state` message tells it and a rematch keeps it. **Everything is odd**: sides 3 to 19, one side may differ from the other, and a row of 3, 5, 7 or 9 that is never longer than the longest side. The start screen offers three presets, **Klassiek** 3 × 3 with three in a row, **Groter** 7 × 7 with five and **Groot** 15 × 15 with five, and **Eigen veld** with a list of the odd numbers for width, height and row. The picker **suggests the row** that makes a good game (`suggestedRow` in `src/play/field.ts`): five in a row, the classic, as soon as the field is big enough (three on 3 × 3), seven on the biggest fields (17 and 19), following the smaller side; it follows the field while it is the row in use and keeps a row somebody chose. The game on one screen and "Speel opnieuw" from a played game choose and keep the field in the same way.
- **The board is a grid of lines, not a field of boxes.** The # of tic-tac-toe: a line _between_ every two columns and every two rows and none around the field (a 3×3 has two lines across and two down), so the field has no edge to fall off, which also suits the bigger fields and the field that grows (#44). The cells have no border, radius or gap and touch each other; the whole cell up to the line is the tap target. The lines are one SVG behind the cells (`Board.tsx`, `lines.ts`), in units of one cell, with the pen at a constant width (`vector-effect: non-scaling-stroke`), so nothing moves when a cell gets a shape. Every line is in the SVG twice, straight and as a hand draws it (a little crooked, started and stopped a little off, a different weight from line to line, the same every time), and the look shows the one it draws with: **Getekend** by hand in the ink (4 px on a small field, down to 2 px from about 7 columns), **Speels** thick and round in the colour of the edge (6 px, down to 3 px; in the dark scheme the edge is black like the page, so it takes the line token), **Rustig** thin and straight (2 px) in the line token. Lines are `--line` or darker, which has 3:1 against the page. The shapes are always on `--page` (their contrast is tested against it), so the field is a surface of that colour, half a rem round the grid and without an edge, over whatever is behind it (a wallpaper, a sky). A cell is no box any more, so what marks it is drawn on a patch inside it (a rounded square a little smaller than the cell, so it keeps away from the lines; the tap target is still the whole cell): the cell you can play gets a tint under the pointer or a finger (a taken cell never does), the move just played in a replay a tint and a thin ring, the keyboard's cell the focus ring, and every cell of a winning line an orange-yellow background (the win colour at half strength over the page, so the shape on it keeps its contrast; cells of several lines at once are all marked, a corner once, and the cells of a line touch, so a win is one band). That a winning cell is told apart by its patch and not by colour alone rests on the band's shape; the replay's thin ring says which move won. Dense mode (thin lines and small gaps from five columns) is gone with the gaps.
- **A field that doesn't fit the screen is scrolled inside its frame.** A cell is never smaller than 2.75 rem (44 px, a finger), so a field of seven columns just fits on a phone (the cells touch, there is no gap to lose), and a bigger one is scrolled in its frame, in both directions, starting in the middle; the page itself never scrolls sideways. For the keyboard the board is one tab stop, as a grid is: Tab goes in and out, the arrow keys, Home and End move over the cells (a field of 19 × 19 would be 361 stops otherwise). Zooming and a view that follows the action are for #44, where the field grows.
- **Players choose their shape.** The shape _is_ the player: the engine's player id, the `player` of a move and a stored game's players are the shape's id (`cross`, `heart`, …; the ids are in `shared/shapes.ts`). A room has seats (`X`, `O`, in the order of joining) and a shape per seat; the seat is only how the room knows who is who. A player chooses while waiting for the other one, or after joining (`choose` message, validated in the room: the shape must exist and be free); a join may carry the shape this browser had last time (kept in localStorage), which the room takes when it is free, so nothing has to be chosen twice. The game starts when every seat has a shape, and **the room waits for as long as it takes**: there is no default, because someone who is there can choose. From then on **the shapes are fixed for the evening**: a rematch keeps them, and another shape means another room (a choice between rounds would need a pause after every game; it can come later). In a game on one screen each player chooses too, with the cross and the circle ready, and "Andere vormen" after a game goes back to choosing. Games that were stored (or rooms in progress) before this, with the players X and O, are read as the cross and the circle.

## Architecture

- `shared/game/`: the game engine, pure TypeScript with no browser or Node APIs. `GameConfig { width, height, winLength, players[] }`, `applyMove(state, move)` with turn order for N players, and a win and draw check that only looks at the last move in four directions, so it also works on a big field. Version 1 uses `{3, 3, 3, [shape, shape]}`, the shapes the two players have chosen.
- `shared/protocol.ts`: the messages between client and server (zod), so both sides share the same types. A message from a player is `join` (with a token that is kept in the browser, and an optional name), `move` or `rematch`; the server answers every change with the whole room as a `state` (config plus moves; the receiver rebuilds the game with the engine) and tells only the sender about an `error`. `shared/room.ts` has the players of a room, the game of each round and the room codes: four consonants, so they never spell a word.
- `src/`: the React app: board, shapes, lobby. Shapes are a registry of SVG components; a player is assigned one, and the engine only knows a player id.
- `server/`: the room as a Cloudflare Durable Object with WebSocket, and the archive of finished games (`archive.ts` for the object, `archive-store.ts` for its SQL, which is tested on Node's own SQLite). The server is authoritative: it validates every move with the same engine from `shared/` and sends the new state to all players. Clients only send `{ move: {x, y} }`.

## Shapes and colours

The shapes are drawn by hand: [docs/reference/shapes.png](reference/shapes.png) has the first seven and [docs/reference/shapes-2.png](reference/shapes-2.png) repeats them and adds five more. Twelve shapes, each with its own marker colour (name and number are on the photos):

| Shape                         | Colour           |
| ----------------------------- | ---------------- |
| Cross (X)                     | vivid red 4      |
| Circle (O)                    | royal blue 70    |
| Square                        | grass green 47   |
| Diamond                       | ultramarine 73   |
| Star                          | WG8 (grey)       |
| Plus                          | vivid pink 6     |
| Asterisk, a cross with a line | ice blue 65      |
| Oval (ovaal)                  | viridian 54      |
| Heart (hart)                  | wine red 1       |
| Fort                          | prussian blue 69 |
| Waves (golven)                | orange 23        |
| Gold bar (goudstaaf)          | lemon yellow 35  |

The SVGs follow the hand-drawn lines, so they keep a slightly wobbly, hand-made look, with a line a little thicker than the marker's so that they hold up at small sizes. Twelve shapes means a game can have up to twelve players.

**Colours.** The colour belongs to the shape and is a design token (`src/styles/tokens.css`), with a lighter set for the dark theme. Telling twelve shapes apart at a glance, and being colourful, come before matching the markers exactly; but each colour stays in the _hue family_ of its marker (a window of degrees, in `src/styles/palette.test.ts`: red about 25°, royal blue 245°, grass green 145°, ultramarine 305°, pink 355°, ice blue 215°, viridian 165°, wine red 10°, prussian blue 275°, orange 55°, lemon yellow 95°, read from the photos). Within its window each colour was moved to be as far from all the others as possible, by a search (OKLab distance, also as seen with red-green colour blindness) under these rules: at least 3:1 against the page, at least 80% of the colour a screen can show at that lightness and hue (so no dull colours; the star is grey like its marker), and not neon. Where drawn colours are close (the three reds, the two greens, the three blues, orange and yellow) they are pulled apart by lightness and hue: the wine-red heart and the prussian-blue fort are the dark ones, the cross is a true red, the plus a magenta, the circle a bright blue, the asterisk a cyan. Yellow can't be bright and still have 3:1 on white, so the light theme's gold is as golden as the contrast allows. The test measures all of this, so a later change can't make two shapes look more alike: the smallest distance between two colours went from 6.5 to 10.4 in the light theme and from 4.7 to 8.5 in the dark theme, and under colour blindness from 1.4 to 5.6 and from 1.0 to 5.7.

The second drawing adds the oval, heart, fort, waves and gold bar; the person who drew them chose the Dutch names. Photos from a phone hold the place where they were taken, so only a copy without metadata goes in the repository (`.gitignore` keeps the original HEIC files out).

## Look and feel

Everybody chooses how the game looks, for themselves and per device (localStorage; the two choices are in the footer, which has a place of its own after every screen: a button in a corner that floats over the screen covered what people needed). The footer also holds the links between screens. The gallery of all the shapes ("Alle vormen") is no longer part of the game: it belongs in a style guide. Two choices, both applied before the first paint by `public/appearance.js` (so nothing flashes) and kept up to date by `src/appearance/`:

- **The theme, one of three looks** (`data-look` on `<html>`, `src/styles/look-*.css`). All three dress the same screens and share one layer (`look-shared.css`): everything centred, a fluid type scale, a board as big as the room that is left (width and height), screens that slide (a view transition, off for people who want less motion), and the shapes always on `--page` so their tested contrast holds. **Getekend** (the first) is warm: paper, marker lines that are a little crooked, a highlighter under the headings (Patrick Hand). **Speels** is bright: a colourful sky, big cards with a thick edge and a hard shadow, buttons that go down when pressed (Fredoka). **Rustig** is calm: big type, no frames, one big button, almost no wallpaper (the system's rounded font). The decision was to keep all three and let people choose, rather than to pick one; the fonts are under the SIL Open Font License, come from the site itself and are fetched only by the look that uses them.
- **Light or dark** (`data-scheme`): it follows the system until a person picks one, and has two buttons, Licht and Donker, never a "Systeem" (the model of [Blokhut](https://github.com/VincentSmedinga/blokhut) and of Lea Verou's [two states are enough](https://lea.verou.me/blog/2026/dark-mode-toggles-two-states-are-enough/)): a pick that is what the system gives anyway is forgotten, so the system is never out of reach. The browser's bar takes the colour of the page (`--chrome`, which a look may set itself).

The wallpaper (the twelve shapes scattered over the page, drawn from the same paths) is a component whose loudness is a token of the look.

## Milestones

- **0 · Foundation:** project, CI, deploy.
- **1 · Playable 3×3:** the engine with tests, board and shapes, two players locally on one screen (to prove the engine and the UI).
- **2 · Online:** room server, create and join a room with a code, live moves, reconnecting.
- **3 · Big field:** configurable size and winning length, three or more players, choosing a shape, a field that grows with the game.
- **4 · History:** finished games are saved and can be watched again move by move, from a list of played games or a link. The engine already keeps the moves (milestone 1), so this builds on that.
