# AGENTS.md

Tic-Tac-Toe Ultra is a game Vincent is building with his family: many players on one big field playing noughts and crosses together, with more shapes than X and O. Version 1 is plain tic-tac-toe (3×3, two players), built so that a bigger field, more players, "k in a row" and more shapes are configuration and new drawings afterwards. All product and architecture decisions are in [docs/plan.md](docs/plan.md); read it before changing anything substantial, and update it when a decision changes.

This file is the way of working for everyone who changes this repository, people and coding agents alike.

## Language

- Code, comments, commit messages, issues and pull requests: English.
- Everything the players see: Dutch. Short, friendly sentences.

## Way of working

- **Planning.** Work is planned as GitHub issues in milestones (`0 · Foundation`, `1 · Playable 3×3`, `2 · Online`, `3 · Big field`, `4 · History`), labelled `app` (the frontend), `server` (the room server), `game` (the game engine and rules), `ops` (CI, deploys, tooling), `docs` or `bug`. The [project board](https://github.com/users/VincentSmedinga/projects) "Tic-Tac-Toe Ultra" shows them: add a new issue there too and move it along the Status column (Todo, In Progress, Done). Closed issues and merged pull requests move to Done by themselves. Tick an issue's checkboxes before or right after each item is done, not in a batch later. A pull request says `Closes #n` only when merging it finishes all of that issue's boxes (a box such as "the family tries it" can be ticked afterwards); otherwise it says `Part of #n`.
- **Pull requests only.** Every change goes through a pull request from a branch. `main` only changes by squash-merging a pull request. The first commit, with this documentation, is the one exception. A ruleset on `main` (Settings, Rules) makes a pull request, one approval and the `Checks` check a condition for merging, allows squash merges only, and refuses force pushes and deleting `main`; the repository's admins can bypass it on a pull request.
- **Authors.** Whoever writes a change is its author, so that someone else can review it: GitHub doesn't let anyone approve their own pull request. A coding agent commits under its own name, with the person who runs it as the committer, and opens its pull requests as itself, with Vincent as reviewer. Claude Code commits as `Claude <noreply@anthropic.com>`, set in `.claude/settings.json`, and works on GitHub as the `smedinga-claude` app (see [CLAUDE.md](CLAUDE.md)).
- **Branches.** Short and descriptive: `game-engine`, `shape-gallery`.
- **Commits.** Small and focused, one concern each, so the history explains itself. Use [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): subject` in the imperative, plus a body that says why. Types: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `style`, `build`, `ci`, `chore`. The scope is optional and names the area: `game`, `app`, `server`.
- **CI.** GitHub Actions (`.github/workflows/ci.yml`) runs on every pull request (a draft gets the checks but no deploy) and on pushes to `main`: the `Checks` job (the Conventional Commits title of the pull request, `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test` and `pnpm build`), then the `End-to-end` job on pull requests (`e2e/`: two Chromium browsers play a whole game, a rematch, a dropped connection and a reload against the production build), the `Style guide` job (builds Storybook, see Structure, and deploys it to an address of its own), and the `Deploy` job. The `Checks` job also fails when the game's build holds any Storybook. The title is checked first and from GitHub as it is now, so after fixing a title, re-run the failed `Checks` job; editing a title also runs the small `Pull request title` workflow (`pr-title.yml`), which isn't required. Keep the pattern of both in sync. The repository is public, so Actions minutes are free and everything runs on every pull request. Actions are pinned to a commit with the version in a comment. A new check that must pass is added to the ruleset by name.
- **Deploys.** The app is a Cloudflare Worker with static assets (`wrangler.jsonc`, the Worker in `server/index.ts`, built with `@cloudflare/vite-plugin`). The `Deploy` job puts the build that `Checks` made on Cloudflare with `wrangler deploy`: a ready pull request as a Worker of its own, `tic-tac-toe-ultra-pr-<number>`, whose address CI comments on the pull request (`preview-cleanup.yml` deletes it when the pull request closes), and `main` as production, `tic-tac-toe-ultra`. After a deploy it checks that the page and `/api/health` answer. It is skipped, with a notice, for a draft, for a fork, and until the one-time setup in the README is done. `public/_headers` holds the security headers; a full Content-Security-Policy comes with the rooms.
- **Pull request.** A Conventional Commits title (it becomes the squash commit on `main`), a body that says what changes and why, `Closes #n` for finished issues, and the milestone. Fill in the template. Open it as a draft while the work is in progress and mark it ready when it's worth reviewing.
- **Screenshots.** A change people see shows one to three essential screenshots in the pull request, on a phone or a tablet and in the light and the dark theme where the theme matters. GitHub has no upload for a pull request's body from the command line, so the pictures live on the `pr-screenshots` branch, which holds nothing else and is never merged: one folder per pull request, `pr-<number>/`. Add them with a worktree (`git fetch origin pr-screenshots && git worktree add .claude/worktrees/pr-screenshots pr-screenshots`), copy the files into `pr-<number>/`, commit and push, then embed them with `![What it shows](https://github.com/VincentSmedinga/tic-tac-toe-ultra/blob/pr-screenshots/pr-<number>/<file>.jpg?raw=true)`. Never take them with anything private in them.
- **Keep AGENTS.md current.** A pull request that changes how we work (a convention, a command, a folder, a pattern) updates this file in the same pull request. This file describes what exists: add CI, commands and folders here when they arrive.

## Commands

Node 24 and pnpm 12 (`corepack enable` or a global pnpm).

| Command                             | What it does                                                                                                                          |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm install`                      | Install dependencies                                                                                                                  |
| `pnpm dev`                          | Start the app and the Worker on http://localhost:5173                                                                                 |
| `pnpm build`                        | Typecheck and build the app and the Worker into `dist/`                                                                               |
| `pnpm preview`                      | Serve the build (app and Worker) as Cloudflare does                                                                                   |
| `pnpm check`                        | Everything CI checks, except the build: types, lint, formatting and tests                                                             |
| `pnpm typecheck`                    | Check all TypeScript projects                                                                                                         |
| `pnpm lint`                         | ESLint (strict type-checked TypeScript, React hooks, a11y)                                                                            |
| `pnpm storybook`                    | The style guide on http://localhost:6100: the shapes, the tokens and the parts, with the three looks and light or dark in the toolbar |
| `pnpm build-storybook`              | Build the style guide into `storybook-static/` (CI does, and deploys it; it is not part of the game)                                  |
| `pnpm test:e2e`                     | Build, then two browsers play a game against the build with the real Durable Object (once: `pnpm exec playwright install chromium`)   |
| `pnpm test` / `pnpm test:watch`     | Vitest, once or in watch mode                                                                                                         |
| `pnpm format` / `pnpm format:check` | Format with Prettier / check formatting                                                                                               |
| `pnpm icons`                        | Make the app icon's files in `public/` again, from the shapes' paths (`scripts/icons.ts`)                                             |

Tests sit next to the code as `*.test.ts(x)`: in `src/` they run in jsdom, in `shared/` and `server/` in Node.

## Structure

| Folder            | Holds                                                                                                                 |
| ----------------- | --------------------------------------------------------------------------------------------------------------------- |
| `shared/game/`    | The game engine: pure TypeScript, no browser or Node APIs, used by both the app and the server                        |
| `shared/`         | What the app and the server share: the engine, `protocol.ts` (the WebSocket messages, zod) and `room.ts`              |
| `src/`            | The React app: board, shapes, lobby                                                                                   |
| `server/`         | The Worker (`index.ts`) and the rooms (Durable Objects); the server is authoritative                                  |
| `service-worker/` | The service worker's source and the build step that writes `sw.js`                                                    |
| `e2e/`            | The Playwright tests, which need the build and a browser                                                              |
| `scripts/`        | Tools that make files: the app icon (`icons.ts`), with its test                                                       |
| `.storybook/`     | The style guide's set-up (Storybook, its own Vite config); `src/**/*.stories.tsx` and `src/styleguide/` are its pages |
| `docs/`           | The plan and decisions; `docs/reference/` holds source material such as the drawn shapes                              |

`shared/game/` exists: `createGame` and `applyMove` (`game.ts`, exported through `index.ts`) are the rules (a won game has `lines`: every line the last move completes, so a corner can win a row and a column at once), immutable and without side effects, so import the engine from `shared/game/index.ts` and never reimplement a rule in the app or the server. A game is its `config` plus its `moves` (kept in the `GameState`): that is what gets stored, and `replayGame(config, moves)` and `stateAfter(state, count)` (`replay.ts`) read it back and step through it. A room is a Durable Object (`server/room.ts`, SQLite storage, WebSocket Hibernation API) that only connects Cloudflare to code you can test without it: `room-logic.ts` holds the rules (the field and the number of seats of the room, who sits where and who may start the game, choosing a shape, whose move, rematch) as functions on a `RoomState` of `{ round, seats, moves }`, a seat being `{ token, id: 'X' | 'O', name?, shape? }` (the player of the game is the shape: `shared/shapes.ts` has the ids, and `roomConfig(round, shapes)` the game; `upgradeRoom` reads a room stored before shapes could be chosen), the game itself being rebuilt from the moves with the engine, and `room-session.ts` decides what happens when a socket says something or goes away, through a `Host` interface that the Durable Object implements and the tests fake. The Worker routes are in `server/index.ts` (`POST /api/rooms`, `GET /api/rooms/:code`, `GET /api/rooms/:code/ws`, `GET /api/games/:id`). When the move that wins or draws a round is played, the session gives the game an id and hands it to the `Host`, whose Durable Object saves it in the archive (`server/archive.ts`, a second Durable Object class that holds every finished game; `archive-store.ts` is its SQL, tested with `node:sqlite`, which is why that one test is typed by `tsconfig.node.json`); the game waits in a queue in the room's storage (`server/archive-queue.ts`, tested with a fake host) until the archive confirms it, and the room's alarm tries again when that fails; `gameId` in the `state` message says where the game of a finished round is kept, and only once the archive has it, and The room notes when the first move of a round was played (`startedAt`, from `Host.now()`), and a `StoredGame` carries it next to `finishedAt`; `GET /api/games/:id` answers a `StoredGame` (`shared/protocol.ts`) to anyone who has the id. `GET /api/games` answers the games of one browser, newest first, a page at a time, as `GameSummary`s: the token is in the `X-Player-Token` header (never in an address), is hashed and looked up in the archive's table of who sat at what, and the answer is `private, no-store`; a page continues after the last game of the one before (`next`), so new games don't make it skip or repeat one. `GET /api/stats` answers the statistics of all finished games together (`Stats` in `shared/protocol.ts`, worked out by `computeStats` in `shared/stats.ts` from `ArchiveStore.all()` every time, cached by the browser for 30 seconds; the rooms made and the rounds of each come from the `rooms` table and the `room_id` of a game, which a room gets when it is made (`room-id` in its storage) and hands over with every game, never inside the stored game; it holds only counts and shapes, never a name, a token or the moves of one game; days and hours are Dutch time, and anything about duration leaves out games without a `startedAt`). `GET /api/stats/mine` counts the games of one browser (`OwnStats`, from `ArchiveStore.ownGames` and `computeOwnStats`; the token is in the `X-Player-Token` header and the answer is `private, no-store`), and the page of played games shows it in `stats/OwnStats.tsx`; which player a browser was in a game comes from `player_id` in the `players` table, which `save` takes from the position of the owner among the owners, the same as the position of the player among the players (so keep `Finished.owners` in the order of `players`). Players' tokens are stored only as hashes, and a game that isn't finished is not kept. Every message is validated with the schemas in `shared/protocol.ts`; a server message is a full `state` snapshot (who sits where with which shape, and, once every seat has a shape, config plus moves, which the receiver replays) or an `error`. A client says `join` (optionally with the shape it had last time), `choose` (a shape, until the game starts), `start` (only the first seat, to begin with fewer people than seats), `move`, `undo` (takes back your own last move while the game is on and the next player hasn't moved, `undo` in `room-logic.ts`) or `rematch`; the state tells how many `seats` the room has. Tokens identify a browser and never leave the server. The Node tests use a stub for `cloudflare:workers` (`server/testing/`); the real Durable Object is tested end to end with two browsers (milestone 2, #11). In `src/`, `shapes/` holds the twelve shapes of the drawn sets: `shapes.ts` is the registry (id, Dutch name, the marker's name) and the drawings, `ShapeIcon` draws one in its own colour. The colours are tokens in `src/styles/tokens.css`, named after the shape (`--shape-cross`), with a lighter set for the dark theme; tests keep every shape at 3:1 against the page and the twelve colours apart from each other (also for red-green colour blindness), colourful and in the hue family of their marker (`src/styles/palette.test.ts`, with the colour arithmetic in `src/styles/color.ts`), so check that when you change a colour: the failing message says which pair is too close. `appearance/` is how the game looks, chosen per device: `look.ts` (the three looks, `data-look`), `scheme.ts` (light or dark with the two-button model of Blokhut, `data-scheme`, the browser bar's `--chrome`), `AppearanceControls.tsx` (the two choices, always visible, in the footer) and the `Wordmark` (the title with the app icon to its left, an `<img>` of `public/icon.svg`, as high as the title's two lines; a look sets `--title-size` and may give `.wordmark-logo` an edge) and `Wallpaper` of every screen; `public/appearance.js` sets both before the first paint (keep it in sync with the two modules), and `src/styles/look-shared.css` plus `look-drawn.css`, `look-playful.css` and `look-calm.css` do the painting under `html[data-look=…]` (dark is `[data-scheme='dark']`, never a `prefers-color-scheme` query: tokens.css holds the colours of both schemes, and a test reads them from there). A new screen has to look right in all three looks, light and dark. `motion/` is how the game moves (decision in docs/plan.md, Animations; the ideas are issue #31): `random.ts` is a seedable generator (`createRandom`, `seedFrom`), `arrival.ts` picks how a shape is written, a pure function of (seed, number of the move, the lengths of the strokes, from `shapes/length.ts`) into an `ArrivalPlan` (a variant that is never the one of the move before, and the order, direction, delay and duration of every stroke: every shape takes the same 0.8 to 1 second, `MIN_ARRIVAL_MS` to `MAX_ARRIVAL_MS`, shared out over its strokes by length, so that one speed holds for all of them), `play.ts` plays a plan on a shape's SVG with the Web Animations API and returns what cancels it, and `preference.ts` is the Animaties switch (Aan or Uit in the footer, per device) on top of `prefers-reduced-motion` (`useMotion`: full, gentle, which only fades, or off). The rules for any animation: only transforms, opacity and SVG strokes, never anything that changes the size of a cell or moves the board; the game state never waits for it (a move counts at once, and the writing of earlier shapes carries on while the next is placed, so a fast replay shows nothing cut off; a rematch, or a shape that is taken off the field, stops it); the finished shape is the element's own style and the animation only hides what isn't there yet, so cancelling it leaves the whole shape; nothing flashes more than three times a second; no animation library; the status line and screen readers are not touched. `Board` asks `useArrival` (`play/useArrival.ts`) which shapes arrived since it was first shown (one new shape at a time; a board first shown with moves, or a jump over several moves, writes nothing) and gives each of those `ShapeIcon`s its `arrival`, which sets `data-arrival` to the variant and plays it before the first paint; `seed` fixes it (tests, later the replay), otherwise a board has a seed of its own. A new animation gets its variants in `arrival.ts` (or a file of its own next to it) with a test of the picker, and a story. The app icon (`public/icon.svg`, `favicon.svg` and the PNGs, `manifest.webmanifest`) is made by `scripts/icons.ts` from `PATHS` and the dark colours of `tokens.css`: run `pnpm icons` after changing a shape or a colour, and `scripts/icons.test.ts` fails when the files are out of date; `index.html` links the icons and the manifest and holds the iOS tags. The game is installable: `service-worker/worker.ts` is the service worker, which is not served as it is, but turned into `sw.js` by the Vite plugin in `service-worker/build.ts` when you build (with the build's files in front of it and the cache named after them; there is none in `pnpm dev`). It never touches `/api/*` or a WebSocket, fetches every screen from the network and answers with `public/offline.html` ("Geen verbinding") only when that fails, keeps the build's `/assets/*` files, and takes over at once; `src/pwa/register.ts` registers it (in a build only), asks for a new one when the app wakes and loads the page again for a new version when the app is out of sight, and `src/pwa/InstallHint.tsx` in the footer is the "Installeer de app" button (`beforeinstallprompt`) and the iOS tip "Tik op Deel en kies Zet op beginscherm", which can be closed for good. Change the worker with its test (`service-worker/worker.test.ts`): a rule it has is that it never answers `/api/*`. Playwright's offline mode stops a navigation before the worker sees it, so the offline page is not in `e2e/`. The page is `.app` with a `header` (the wordmark), the screen in `main` and `SiteFooter` (`src/layout/`), a real `contentinfo` landmark after `main`, which holds the links between screens ("Terug naar het begin", "Gespeelde spellen", "Statistieken", the one for the screen you are on left out) and the appearance controls: nothing is fixed over the screen, so a control never covers what a screen needs, and a link to another screen belongs in the footer, not at the bottom of the screen. A button is as wide as what is on it. `play/FieldPicker.tsx` and `field.ts` choose and describe the field of a game (presets, an own field with odd numbers only, the suggested row; the limits and `isValidField` are in `shared/room.ts`, which the room, the protocol and the picker share); `Board` is a frame (`.board-frame`) with the grid in it: the frame scrolls what doesn't fit, the grid is one tab stop with arrow-key navigation, and `--columns`, `--rows` and `--cell-min` size it in `Game.css`. The board is a grid of lines and not of boxes: cells have no border, radius or gap and touch each other, and the lines between them (none around the field) are one decorative SVG behind the cells (`lines.ts` makes them, in units of a cell, each line twice, straight and by hand, with a weight and the same wobble every time). A look sets `--board-max`, `--line-width`, `--line-color` and `--cell-radius` and shows `.board-line-straight` or `.board-line-hand`: Getekend by hand in ink, Speels thick and round in the edge's colour (the line token in dark), Rustig thin and straight; a cell is marked on `.cell::before`, a patch a little smaller than the cell that keeps away from the lines (hover tint, `data-last` tint and ring, `data-winning` an orange-yellow background), and the focus ring is inside it too, never a border. The field is a `--page` surface so the shapes keep their contrast over a wallpaper. Never put a gap or a border on `.cell`: `Board.test.tsx` and `styles/board-lines.test.ts` read the CSS for it. `replay/Replay.tsx` looks at a game again, given a config and its moves (and optionally who sat where): buttons, a slider, the arrow keys, Home and End, and an autoplay at one speed (`STEP_MS`, 1.2 seconds a step: a shape takes at most a second to write, so a step is done, and rests a moment, before the next begins; there is no choice of speed) (a step has a triangle and a bar, ◀| and |▶, a jump to the start or the end two triangles, |◀◀ and ▶▶|, and play is alone a round, solid, bigger button in the middle, with two bars while it plays, so that none of them is taken for another: a look may not make play a pill or a square, `Replay.css` holds it above the looks); it only reads the game with the engine's `replayGame` and `stateAfter`, so it works for any field and any number of players, and both the game on one screen and a room offer it with "Kijk terug" once a game is over. `games/` is the games that were played: `GamesPage` (`/spellen`, "Gespeelde spellen") lists the finished games of this browser and `GamePage` (`/spel/<id>`) opens one with the replay, the link to copy and "Speel opnieuw" (a new room: every game is still the classic one, so the same players and field is just another room), both through `games/api.ts`. `stats/` is the page Statistieken (`/statistieken`): `StatsPage` asks `GET /api/stats` through `stats/api.ts` and shows cards for the totals and the weeks, how long games take, the shapes, whether starting wins, each kind of game with two heat maps (first moves, winning cells), when people play and a few fun ones, in Dutch and in all three looks (the look paint is at the bottom of `Stats.css`, so a look file needn't change); a card for the rooms and rematches; a card for the rooms and rematches; with fewer than three games it says "Nog te weinig spellen" instead of averages (`MIN_GAMES`). The charts are in `Charts.tsx`, CSS bars and SVG heat maps with no chart library, and each says its numbers in text (every bar is a list item for screen readers, a heat map names its busiest cells in words), so never only in colour. `online/` is the way into a game with someone else: `route.ts` and `Link.tsx` are a minimal router (`/` the start screen, `/samen` the game on one screen, `/kamer/<code>` a room, `/spellen`, `/spel/<id>` and `/statistieken`; the Worker serves the app for every address), `identity.ts` keeps this browser's token, name and the room it last sat in (the start screen offers the way back to it, as long as the room exists) in localStorage (with a fallback to memory when it is off), `api.ts` makes and looks up rooms, `useRoom.ts` is one player's connection to a room (first asking whether it exists, then the WebSocket, joining with the token; a lost connection is tried again by itself, after 0.5 s growing to 8 s, and at once when the phone wakes up or the network is back, never when the room is gone or full), `StartScreen.tsx` (a new room: the number of players, the field), `RoomPage.tsx` (the lobby with the code, who is there, the free seats, the start button of the first seat and the shape picker, until `isStarted` in `started.ts` says every seat has a shape) and `OnlineGame.tsx` (the board of a room, which only follows the server's `state` and sends a move or a rematch) are the screens. The tests drive the room page with a fake socket (`RoomPage.test.tsx`). `play/` is the game on one screen: `Game` keeps the state with the engine from `shared/game/`, `Board` draws it as a grid of buttons, and `players.ts` reads a player id as a shape (the id is the shape's id; X and O only occur in games stored before shapes could be chosen). `Game` starts with `ShapePicker`, the twelve shapes as buttons, once per player; the player who starts alternates every round. The interface colours (`--line`, `--win`, `--focus`) are tokens as well, with a test for their contrast. The style guide is Storybook (decision in docs/plan.md, Style guide): a part of the game gets a story next to it (`Board.stories.tsx`), the pages that belong to no part (the shapes, the tokens, the buttons and cards) are in `src/styleguide/`, and the tokens page reads `tokens.css` and the page's custom properties, so a new token or shape shows up without touching it. Its toolbar sets `data-look` and `data-scheme` with `applyLook` and `applyScheme`, so a story shows what the game shows; nothing in the game may import a story or `.storybook/`, because the game's build must hold no style guide (CI checks). A new part or state that people see gets a story in the same pull request. The tooling follows [Blokhut](https://github.com/VincentSmedinga/blokhut). TypeScript stays on 6.0 until typescript-eslint supports 7.
